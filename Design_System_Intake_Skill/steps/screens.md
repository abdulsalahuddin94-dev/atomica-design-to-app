# Screens: sizes, Design file audit, flows, fidelity

Part of `Design_System_Intake_Skill` (sections keep their original numbers, so "section 7c" etc. still resolve; the map is in `SKILL.md` section 0c). Load only when screens are built or changed (0.8 = Yes, Brownfield rebuilds, flows). Every `Ask (choice)` / `Ask (multi)` here also gets a "Back" option (`SKILL.md` section 0, Back on every menu).

## 7d. Screen sizes (Abdul's rule, every path that builds screens)

**Design file audit (Abdul's rule, every time screens are built or changed):** run audit-design-system (ds-auditor, `screens` mode) on that Design file to confirm it really uses the DS: library components only (no local copies, detached instances or hand-drawn parts), library variables and styles only (no raw values, no variables used for the wrong purpose), latest library version. In a single-file project (`figma.layout` = `single-file`, section 7g) "library" means the components, variables and styles on `figma.ds_pages` of the same file, and there is no library version to check. Fix what it finds, save the report in `<Project folder>/audits/`, and log the result in `CHANGELOG.md` (`Design file audit: <numbers>, report <path>`).

- Screen frame sizes (Abdul, 2026-10-06), every platform:
  - **Desktop (Web):** 1440 wide; height **at least 900**, **default 1024**. A page taller than the default grows the frame (Hug or a fixed taller height), never below 900.
  - **Mobile (Web mobile, iOS, Android):** **375 x 812**. Content longer than 812 scrolls inside the frame (pinned bars stay at 812 per section 7f); a separate long-scroll frame, when the user asks for one, keeps 375 wide.
  - Set width and height explicitly when the frame is created; never leave a screen at a default 100 x 100 or a Hug height of a few hundred px.
  - Frame sizes in a reference's `data/screen-templates.json` (e.g. 402 x 874, 412 x 917) are that reference's own; project screens use the sizes above.
- **Brownfield exception:** keep the sizes of the screens that are already designed in the file, so they are not broken.
- If the existing "screens" are only screenshots (images, not designed frames), they do not set the size: use 375 x 812 / 1440 x 1024.
- **Check:** `tools/check_screens.figma.js` and ds-auditor `screens` mode report every screen frame whose size breaks this rule (outside the Brownfield exception).

## 7e. Multi-screen flows (Abdul's rule, every request for a flow of two or more screens)

A flow (e.g. sign-up, checkout, booking) always runs in this order. For the screens, **Impeccable leads the design** (Abdul, 2026-10-06; it designs, not only audits): `shape` plans each screen (hierarchy, layout, density, type and color use) before it is built, and `critique` + `polish` (plus `layout`, `typeset`, `colorize` or `distill` when the critique asks) run on it after. ui-ux-pro-max is a second reference (patterns, anti-patterns). figma-generate-design + figma-use do the Figma work. Impeccable's code paths (`craft` build, `live`, `generate`) are not used: screens live in Figma. Every Impeccable decision snaps to DS components and variables; a value the DS lacks is proposed as a token (step 2), never drawn raw. On iOS / Android it uses its `ios` / `android` references next to section 11 of the platform Main Skill. **UX rules (2026-10-11):** each screen spec also lists the rules from `Workflow_References/ux/README.md` that match what the screen holds (forms, tables, search, navigation, states, loading...; `spacing.md` and `accessibility.md` always), and the critique reads them back as criteria. Load figma-generate-library + figma-use for any new component.

0. **Flow map first (Abdul, 2026-10-11).** Load `steps/plan-user-flows.md` and map every screen, state (default, loading, error, empty, success) and decision of the flow; approved before the gap table. Its screen list and state matrix feed step 1 and every screen spec.
1. **Flow gap analysis first (no build yet).** When the screens have a visual source (screenshots, existing frames, a mockup), write its screen spec first (section 7f). Split every screen of the flow into sections (e.g. Top Bar, Form, Summary, Button Docked). Produce **one table** for the whole flow: screen, section, element, the DS component that covers it (existing) or `missing`. For each missing component give its tier (Atom / Molecule / Organism) and its atomic structure map (which existing atoms and variables it is built from). Save it in `<Project folder>/audits/<date>-flow-<name>.md` and show it, then Ask (choice): "Approve the gap table?" "Approve (Recommended)" / "Request changes". **Abdul approves the table before anything is built.**
2. **Build the missing components in the DS file, never in the Design file.** Lower tier first, only from existing variables, styles and atoms (Atomic Design golden rule). Each one gets its Figma description (Purpose, Usage Rules, Accessibility), an entry in its group's Component_Skill and `data/component-registry.json`, and an audit (ds-auditor). If a component needs a token that does not exist, **propose it (name, value, Primitive it aliases) and wait for approval** (Ask (multi) when several are proposed: one option per token); never add it silently.
3. **Publish and update the Design file** (single-file projects: save a Figma version instead and skip Accept updates, section 7g). Ask Abdul to publish the library (section 7c) and wait for his confirmation (Ask (choice): "Done" / "Not yet"). Then he runs Accept updates in the Design file; open it, run the file check (section 7c) and **verify the new components appear** in its library before using them.
4. **Build the screens one by one** from library instances and variables only (no local copies, detached instances or raw values), section by section, at the sizes in section 7d (Mobile 375 x 812, Desktop 1440 x 1024 default, height at least 900; Brownfield keeps existing sizes). Follow the screen fidelity rules and the visual loop in section 7f, after an Impeccable `shape` plan for the screen (saved with its screen spec) and before the audit an Impeccable `critique` + `polish` pass (fixes use DS components and variables only). **Audit the Design file after each screen** (ds-auditor, `screens` mode, fidelity checks included) and fix before the next screen.
4b. **Usability review (optional, Abdul 2026-10-13).** When the last screen of the flow passes its audit and Impeccable critique, Ask (choice): "Run a usability review of the whole flow?" "Yes (Recommended)" (description: Nielsen's 10 heuristics and Krug across all screens, each issue rated 0-4; reports only) / "Skip" / "Back". Yes -> ds-auditor `usability` mode on the flow's screens in order, following `Workflow_References/ux-heuristics/README.md`. Show the score and the issues, then Ask (multi): "Which issues should I fix?" one option per issue (or per heuristic when more than 4). Fixes use DS components and variables only (a missing component goes through steps 1-3); each fixed screen gets its Design file audit again. Severity 3-4 issues not fixed or accepted keep the flow from `Ready for review`. Log `Usability review: <score>/10, <n> issues (<b> blocking)` or `Usability review: skipped`.
5. **Prototype question (Abdul, 2026-10-06, after every flow is fully designed).** When the last screen of the flow passes its audit, Impeccable critique and the usability review (4b, when run), Ask (choice): "Do you want to create the prototype?" "Yes" (description: link the flow's screens with click interactions in Figma so it can be played) / "No" / "Back". Yes -> wire the flow in the Design file: one flow starting point on the first screen (named after the flow), an On click -> Navigate to interaction on each tappable instance (buttons, links, list items, tabs, back actions) to the screen the spec says it opens, popups as Open overlay (centered, with the DS scrim), back actions as Back; Smart animate only where the source animates, else Instant. Interactions go on instances in the screen, never on the DS components. Then play-check it (every screen reachable from the start, no dead-end button that the spec says should navigate), list the links made, and record `Prototype: yes / no` in the CHANGELOG entry. No -> record `Prototype: no`; ask again only when the user asks.
6. **Log and ask.** Append the entry to `CHANGELOG.md` (components added, library published, Design files updated, Design file audits, prototype) with `Storybook synced: no`, run `tools/project_status.py`, then Ask (choice): "Update the Storybook now?" "Update now" / "Later".

- Screens that need **no new component** may be built while waiting for the Publish confirmation; screens that use a new component wait for step 3.
- The Screens checkpoint (section 8) shows the whole flow, per mode, with the audit results.

## 7f. Screen fidelity (Abdul's rule, every path that builds or rebuilds screens)

Brownfield trial (2026-09-30): screens built from the text inventory alone, with default instance text and no visual check, passed the DS audit but looked nothing like the source. A screen is done only when it matches its source, not when it only uses the DS.

1. **Look at the source first.** Open every source screenshot or frame at full size (view the image file, or `figma_capture_screenshot` of the frame). `Inputs/Extracted_Tokens.md` is for tokens only; it is never the reference for a screen.
2. **Screen spec** (one file per screen, `<Project folder>/audits/<date>-screen-spec-<screen>.md`), sections top to bottom. Per section: the DS component and variant, every text exactly as shown (keep the original language), icons, item counts (e.g. 8 playlist rows, 3 chips), selected/active states, alignment, full-bleed or inside the gutter, and whether it scrolls, scrolls horizontally or is pinned (status bar, app bar, mini player, bottom navigation), and each bar's width as the source shows it (full-bleed, or inset like a floating mini player). Anything the DS lacks goes in the 7e gap table. The specs are approved together with the gap table (the same Ask (choice)), before any build.
3. **Build rules.**
   - Every text, variant, boolean, icon swap and image slot of every instance is set from the spec (photos: section 7i, `steps/images.md`; never an empty grey box). No default placeholder text may remain ("Label", "Filter", "Track title", "Title"); two instances only share a text when the source does.
   - Item counts match the spec. A list or rail that continues off screen keeps the visible count plus the partial item the source shows.
   - Screen structure: status bar and top bars at the top; mini player and bottom navigation pinned at the bottom (outside the scrolling content); each bar full-bleed or inset exactly as the spec says (a floating mini player stays inset); the gutter applies to the content only. Horizontal rows clip and scroll; they never overflow the screen or squash their children.
   - Fixed-size instances keep their size (no instance narrower than its component's minimum width). Hug or fill is chosen per the spec, never left to overflow.
   - The screen frame's background, padding and gaps are bound to DS variables, like everything inside it.
   - Build one section per script call and check it before the next; never build a whole screen in one script.
   - **Source over platform rules (Abdul, 2026-10-13):** when the source shows a size, glyph size, spacing, color or shape that differs from the platform guideline (Material 3, HIG), match the source and fix the gap in the DS (variant, property or component-level override); never report it as an accepted platform difference. Accessibility floors (touch target, contrast) stay, through the hit area or a nearby token.
4. **Visual loop (mandatory, every screen).** (Runs in the ds-auditor agent, section 0c: it captures and compares, the main session fixes from its list.) After each screen: capture it with `figma_capture_screenshot`, place the capture next to the source image, and compare section by section: order, texts, counts, icons, sizes (within 4 px), colors, pinned bars. Fix and repeat, up to 3 rounds; list what still differs and why. If the capture fails, stop and ask the user to bring the Design file to the front in Figma (section 7c.7), then retry. A screen is never reported as done without its side-by-side images.
4b. **Measured fidelity (mandatory when the source runs: a live app, a local preview of the code, a web page; Abdul, 2026-11-03).** Screenshots side by side miss small differences (a 12 vs 14 px text, a 500 vs 600 weight, a slightly different color, a 16 vs 20 radius), and they add up so the user has to send screenshots after every build. So the comparison is done in numbers, not by eye:
   1. Open the source screen at the Figma frame width (1440 for Desktop, 375 for Mobile), the same shell state (sidebar open or closed as in the Figma screen), the same mode and **the same data record** the Figma screen shows (same person, project or month), after the page has fully loaded.
   2. Run `tools/source_dump.js` in the page (built-in browser javascript tool or Playwright `page.evaluate`) and save its JSON in `audits/` (or the scratchpad).
   3. Run `tools/figma_text_dump.figma.js` on the screen frame (set `SCREEN_ID`; through FigCli eval keep the result in `globalThis` and read it in slices under 20K characters).
   4. `python tools/fidelity_diff.py <source.json> <figma.json> --figma-x0 <sidebar width> --figma-y0 <top bar height> --out audits/<date>-fidelity-<screen>.md`. It matches every text by content and reports size, weight, color (deltaE > 3), line height, position (> 4 px after aligning the shell), all caps, missing texts and box background / border / radius / size.
   5. Fix and re-run until **Open differences is 0**, or each remaining line is explained in the report (e.g. a text that only exists in the code's demo data). Fix order: line heights and gaps first (they shift everything below), then sizes and weights, then colors and radii.
   6. Where the fix belongs: a difference shared by every use of a component is fixed in the DS component (then publish and Accept updates); a one-off is an override on the instance with a DS variable. **An exact value with no matching variable is never silently snapped to the nearest one:** list it (source value, nearest variable, deltaE or px gap) for the user's approval, add the variable after the yes, or record the decision to use the nearest. When the DS is shared or read only, the list goes to `audits/<date>-ds-issues.md`.
   The screenshot loop (step 4) still runs for what numbers do not show (icons, chart shapes, images). A screen is not reported as done without the fidelity report.
5. **Fidelity audit.** ds-auditor `screens` mode includes the fidelity checks (placeholder texts left, counts vs spec, overflowing or squashed children, pinned bars, unbound screen frames). `tools/check_screens.figma.js` does the structural part.
6. **Report, never self-approve.** Show every screen next to its source (each mode the project has) with the audit numbers, and set the Screens checkpoint to `Ready for review`. Only the user's reply sets `Approved` (section 8).
7. **Brownfield `screen-templates.json`:** generated from the approved screen specs of the project's real screens, not copied from a reference entry.
